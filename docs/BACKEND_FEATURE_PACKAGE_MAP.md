# Backend Feature Package Map

Sprint 59 moves the backend toward feature-owned packages while preserving the
existing FastAPI routes, persisted schemas, and service import compatibility.
The migration is incremental: add characterization coverage, move one cohesive
module group, keep compatibility shims for existing imports, run boundary and
behavior checks, then continue with the next feature.

## Dependency Rules

- Routers remain thin HTTP adapters and call feature service entrypoints or
  compatibility service modules during the migration.
- Feature packages may import `app.ai`, `app.common`, `app.core`, `app.db`,
  `app.schemas`, `app.mcp`, and other public `app.features.*` APIs.
- Feature packages must not import `app.services.*` or `app.routers.*`; those
  paths are migration shims and HTTP adapters.
- Cross-feature behavior should use typed DTOs or explicit orchestration
  services, not hidden module-level side effects.
- DB models remain centralized under `app.db.models` for Sprint 59 to avoid
  Alembic churn and circular model imports.
- Scripts should be thin CLIs over package-owned services when logic is shared
  with API routes or tests.

Run the boundary check with:

```bash
python3 scripts/check_feature_boundaries.py
```

## Migration Sequence

1. Add or confirm characterization tests for the workflow being moved.
2. Move cohesive implementation modules into the target `app.features.*`
   package.
3. Leave the old `app.services.*` module as a compatibility shim when external
   callers still import it.
4. Update eval scripts and docs that hard-code source paths.
5. Run `python3 scripts/check_feature_boundaries.py`, focused pytest for the
   touched feature, and the full backend suite when practical.
6. Remove compatibility shims only after routers and callers have migrated.

## Shared Duplication Disposition

Use this section for `G49-D`. Sprint 59 centralizes only behavior that is shared
by multiple features and already has parity coverage. Feature-specific prompt
copy, Markdown format, proposal UX copy, and orchestration stay in their owning
feature or service until tests prove a shared abstraction would reduce real
duplication without hiding product behavior.

| Cleanup target | Sprint 59 disposition | Owner | Reason |
|---|---|---|---|
| Structured-output schema instructions and repair prompts | Shared schema-instruction construction is centralized; repair dispatch remains in the AI gateway. | `app.ai.structured_output` | Streaming and non-streaming model calls share `schema_instruction_message`; repair attempts still need gateway-level completion accounting and provider calls. |
| Deterministic fallback completion metadata | Centralized. Workflow services keep private wrappers only for stable fallback names and route behavior. | `app.ai.fallback_completion` | Multiple AI workflows need the same provider mode, fallback reason, token/cost, timeout/cause, and redacted failure metadata. |
| Metadata merging | Centralized for ordered list-like JSON metadata. | `app.common.metadata` | Evidence, workflow, and feature packages use consistent merge behavior without importing service modules. |
| Retrieval result shaping | Centralized for pure result fusion, score math, diagnostics, and context selection helpers. | `app.features.retrieval.*` | Retrieval execution, SQL/vector access, cache lookup/write, and route orchestration still depend on DB/session settings and stay service-owned. |
| Citation/provenance shaping | Centralized where shared across artifact workflows: citation verification, citation de-dupe, retrieved-ID checks, source provenance, guide citation drilldowns, and research citation audits. | `app.features.evidence.*`, `app.features.guide.citations`, `app.features.research.citation_audit` | Artifact-specific support decisions, persistence, and route responses remain service-owned until typed citation outcome DTOs are introduced. |
| Tool audit/proposal payloads | Centralized for pure audit metadata, approval summaries, and proposed-change payloads. | `app.features.governance_tools.audit` | Authorization, redaction before persistence, approval writes, audit writes, and commits remain service/governance boundaries. |
| MCP protocol envelopes | Centralized for JSON-RPC envelopes, tool schema annotations, validation, and MCP audit/input metadata. | `app.features.mcp.protocol` | Stdio/HTTP transport, auth context construction, redaction persistence, and request commits remain adapter-owned. |
| Proposal/action-card creation | Feature-owned, not globally centralized. | `app.features.guide.actions`, `app.features.guide.routing`, `app.features.decisions.recommendation`, `app.features.research.proposals` | These payloads encode different UX and approval semantics; centralizing them now would create a vague shared utility layer. |
| Markdown rendering | Feature-owned, not globally centralized. | `app.features.validation.plan_rendering`, `app.features.research.memo_rendering`, `app.features.decisions.recommendation`, eval report writer | Markdown formats differ by artifact/report type and are pinned by feature tests. |
